# Руководство по выпуску

## Политика веток и версий

Для повседневной разработки используется `main` плюс краткоживущие функциональные ветки, слияние выполняется через Pull Request. Исправления также выпускаются из `main`; долгоживущие ветки выпуска пока не поддерживаются.

Версия централизованно поддерживается в `Directory.Build.props` в корне репозитория. Сопровождающий выбирает следующую версию в зависимости от изменений:

| Изменение | Изменение версии | Пример |
| --- | --- | --- |
| Обратно совместимое исправление | patch | `1.0.26` → `1.0.27` |
| Обратно совместимая новая функция | minor | `1.0.26` → `1.1.0` |
| Несовместимое изменение интерфейса, команд или формата файлов | major | `1.0.26` → `2.0.0` |

Для стабильного выпуска в `VersionPrefix` указывается `A.B.C`, а `VersionSuffix` оставляется пустым; для предварительного выпуска в `VersionSuffix` указывается `alpha.N`, `beta.N` или `rc.N`, где `N` — положительное целое без ведущих нулей. Например, `VersionPrefix=1.0.27` и `VersionSuffix=rc.1` соответствуют `1.0.27-rc.1`; не записывайте суффикс в `VersionPrefix`. При преобразовании кандидата в стабильный выпуск очистите `VersionSuffix`.

GitHub Actions читает полную версию из конфигурации и автоматически создаёт соответствующий тег `vA.B.C` или `vA.B.C-rc.N` и т. п. Информационная версия выпускаемого EXE сохраняет суффикс предварительного выпуска; файловая версия и версия сборки используют четыре числовых сегмента `A.B.C.0`. Числовые сегменты в репозитории ограничены диапазоном `0..65534` для совместимости с версиями сборок .NET; при отправке в Microsoft Store первый сегмент также должен быть больше `0`, версия MSIX — `A.B.C.0`.

## Выпуск EXE через GitHub Actions

### Подготовка выпуска

1. Убедитесь, что лицензия GPL-3.0-or-later, политика конфиденциальности и контактные данные поддержки соответствуют требованиям текущего распространения. При выпуске сохраните тег, указывающий на коммит сборки, и в том же Release предоставьте полный соответствующий исходный код этой версии и инструкции по сборке, чтобы исходный код можно было получить вместе с EXE/MSIX; проверьте, что автоматически созданный GitHub архив исходного кода содержит файлы, необходимые для сборки. При обновлении зависимостей или self-contained .NET runtime синхронно обновляйте [уведомления о сторонних компонентах](../THIRD-PARTY-NOTICES.txt). Лицензия проекта, уведомления о сторонних компонентах и лицензии шрифтов встроены в приложение и доступны офлайн на странице «О программе»; границы лицензирования см. в [LICENSE-NOTICE.md](../LICENSE-NOTICE.md).
2. В функциональной ветке измените `VersionPrefix` в `Directory.Build.props` (для предварительного выпуска также задайте `VersionSuffix`) и перенесите содержимое этого выпуска из раздела `Unreleased` в `CHANGELOG.md` в соответствующий раздел версии. Сохраните `## Unreleased` для дальнейшей разработки.
3. Заголовок раздела версии должен иметь форму `## [1.0.27] - YYYY-MM-DD` или `## [1.0.27-rc.1] - YYYY-MM-DD`; замените заполнитель даты на фактическую дату выпуска, содержимое раздела не должно быть пустым. Для предварительного и стабильного выпуска нужен отдельный раздел версии, точно соответствующий тегу; начиная с этого выпуска новые разделы версии должны, согласно приведённому ниже соглашению, содержать журнал на китайском и английском языках.
4. Поместите конфигурацию версии и журнал выпуска в один PR подготовки выпуска, убедитесь, что рабочий процесс `build` проходит, и выполните слияние в `main`. Диапазон изменений этого push должен одновременно включать оба файла, а полная версия в конфигурации должна фактически измениться — только тогда запустится автоматический выпуск.
5. GitHub Actions выполняет проверки, автоматически создаёт тег версии и формирует черновик Release; сопровождающий проверяет его и вручную публикует.

Например, для будущего исправления в `Directory.Build.props` задаётся:

```xml
<VersionPrefix>1.0.27</VersionPrefix>
<VersionSuffix></VersionSuffix>
```

Одновременно в `CHANGELOG.md` добавляется непустой раздел `## [1.0.27] - YYYY-MM-DD` с фактической датой; после слияния в `main` автоматически создаётся тег `v1.0.27`. Для кандидата в релизы `VersionSuffix` задаётся как `rc.1`, а версия в журнале записывается как `1.0.27-rc.1`.

### Двуязычный журнал выпуска

В последующих выпусках в одном разделе `## [версия] - дата` последовательно используются `### 中文` и `### English`. Оба набора пунктов описывают одни и те же факты изменений, ограничения и результаты проверки; английский текст должен полностью переводить соответствующий китайский, не опускать предупреждения и не добавлять непроверенные заявления о возможностях. После подготовки содержимого выпуска сохраните вверху `## Unreleased` для следующего цикла разработки.

Например, структура при подготовке выпуска выглядит так; версия, дата и пункты должны быть заменены фактическим содержимым этого выпуска:

```markdown
## Unreleased

## [1.3.4] - YYYY-MM-DD

### 中文

- 在设置中增加界面语言选择。

### English

- Add interface language selection to Settings.
```

`Get-ReleaseMetadata.ps1` извлекает весь раздел версии и останавливается только на следующем заголовке `## ` или в конце файла, поэтому `### 中文` и `### English` полностью попадают в описание Release. Не записывайте языковые заголовки как `## 中文` или `## English`, иначе раздел версии завершится досрочно. Текущая проверка метаданных подтверждает уникальность раздела версии, действительность даты и непустое содержимое; полнота обоих языков и согласованность пунктов всё ещё требуют подтверждения при проверке выпуска.

После двуязычного журнала рабочий процесс добавляет инструкции по загрузке и запуску на китайском и английском, команды проверки SHA-256, а также соответствующий исходный код и инструкции по сборке. Требования к загрузке, статус отсутствия подписи и ограничения экспериментальной записи сохраняются одинаковыми на обоих языках.

### Автоматические проверки и черновик

`.github/workflows/release.yml` отслеживает изменения `Directory.Build.props` или `CHANGELOG.md` в `main`, но в процесс выпуска переходит только если этот push **одновременно изменяет конфигурацию версии и журнал выпуска, а полная версия меняется**. Обычный push кода запускает только стандартные проверки сборки; добавление только `Unreleased` или корректировка конфигурации без изменения версии не создают Release.

Рабочий процесс читает полную версию из конфигурации, проверяет формат и соответствующий непустой раздел Changelog с датой, подтверждает, что коммит выпуска принадлежит `origin/main`, и повторно использует сборку и регрессионные проверки из `build.yml`. Только после успешного прохождения всех проверок создаются выпускаемый EXE, соответствующий тег версии и черновик; вручную создавать или отправлять тег не нужно.

GitHub Actions создаёт однофайловый Windows x64 EXE, включающий .NET runtime, поэтому отдельная установка .NET не требуется. После упаковки итоговый EXE отдельно помещается в изолированный каталог и запускается; выполняются самопроверка, проверка генерации RAW/WAV на двух секторах и проверка снимков экрана GUI, чтобы подтвердить, что достаточно загрузить один файл, после чего вычисляется SHA-256. В GitHub Release прикрепляется только этот EXE, например:

```text
DiscImageStudio-v1.0.27-win-x64.exe
```

Контрольная сумма SHA-256 записывается в описание Release для проверки после загрузки. Рабочий процесс использует встроенный `GITHUB_TOKEN` для создания **черновика GitHub Release**, настраивать personal access token (PAT) не требуется. Тег предварительного выпуска автоматически устанавливает флаг prerelease; стабильный тег создаёт черновик стабильного выпуска. Он не публикует черновик автоматически и не отправляет его в Microsoft Store и не публикует самоподписанный тестовый сертификат.

Сопровождающий на [странице Releases](https://github.com/JiaFeiMiao-K-Cat/DiscImageStudio/releases) в GitHub проверяет версию, описание выпуска, EXE и контрольную сумму в черновике, загружает и проверяет запуск, после чего вручную публикует. Для вычисления SHA-256 загруженного файла и сравнения со значением в описании Release можно использовать следующую команду:

```powershell
Get-FileHash .\DiscImageStudio-v1.0.27-win-x64.exe -Algorithm SHA256
```

### Повторные попытки при сбоях и исправления

Можно перезапустить неудачный запуск Actions или вручную запустить рабочий процесс `release` из `main` в GitHub Actions. При ручном запуске нет ввода тега: читаются текущая конфигурация `main` и журнал выпуска и выполняются все проверки выпуска; повторная попытка не требует ещё раз изменять файл версии.

При повторной попытке для той же версии существующий тег должен указывать на тот же коммит, что и эта сборка, а существующий Release должен оставаться черновиком. Уже опубликованные Release, теги и артефакты нельзя перезаписывать или перемещать; при обнаружении проблемы исправьте её в `main` и выпустите новую версию, а для итераций предварительного выпуска увеличивайте номер, например `rc.1` → `rc.2`. Если `main` уже продвинулся, а тег той же версии указывает на старый коммит, следует перезапустить ранее неудачный запуск или подготовить новую версию для нового коммита. Даже если изменяется только описание выпуска, следует сохранять факты и запись об исправлении; нельзя заменять уже опубликованные двоичные файлы.

Рекомендуется, чтобы администратор репозитория настроил в GitHub защиту ветки `main`, требующую Pull Request и обязательную проверку `build`; для тегов `v*` следует настроить ruleset, разрешающий рабочему процессу выпуска создавать теги и запрещающий их обновление и удаление. Файлы рабочего процесса не равнозначны настройкам удалённой защиты; эти защиты администратор должен настроить отдельно.

## Локальная тренировочная сборка EXE

В корне репозитория запустите тот же упаковочный скрипт, что и GitHub Actions:

```powershell
powershell -ExecutionPolicy Bypass -File packaging/Build-Release.ps1
```

Скрипт автоматически использует версию из `Directory.Build.props`. Например, при конфигурации `1.0.26` выходной каталог — `artifacts/release/v1.0.26/`. Скрипт собирает и отдельно проверяет self-contained `win-x64` EXE, создаёт `DiscImageStudio-v1.0.26-win-x64.exe` и `SHA256SUMS.txt`; файл контрольных сумм используется для локальной проверки и формирования описания Release рабочим процессом и не прикрепляется к Release. Локальная тренировка не требует наличия тега версии или раздела выпуска в Changelog и не создаёт GitHub Release; официальный выпуск должен удовлетворять всем проверкам выше.

## Microsoft Store MSIX

MSIX — независимый канал ручного распространения. Сначала зарезервируйте имя продукта в Partner Center и скопируйте со страницы Product identity:

- Package/Identity/Name
- Package/Identity/Publisher
- Package/Properties/PublisherDisplayName

Локальный запуск:

```powershell
powershell -ExecutionPolicy Bypass -File packaging/Build-MSIX.ps1 `
  -IdentityName "Partner Center Identity Name" `
  -Publisher "CN=Partner Center Publisher" `
  -PublisherDisplayName "Publisher display name" `
  -DisplayName "Reserved product name"
```

Если `-Version` не указан, стабильная версия читается из `Directory.Build.props` и преобразуется в `A.B.C.0`. Если нужно явно указать версию для магазина, используйте `-Version "1.0.26.0"`; это переопределённое значение также синхронизируется с версией EXE внутри пакета, чтобы манифест и версия программы не расходились. Канал Microsoft Store не принимает суффиксы предварительного выпуска, такие как `-rc.1`; при подготовке пакета для Store следует использовать конфигурацию стабильной версии.

Также можно вручную запустить рабочий процесс `package-msix` в GitHub Actions и заполнить те же значения; если `version` оставить пустым, конфигурация репозитория также будет прочитана. Этот рабочий процесс сначала повторно использует CI из `build.yml`, затем создаёт MSIX как вложение Actions; он не отправляет пакет в магазин автоматически и не прикрепляет его к GitHub Release. Созданный Store MSIX может оставаться неподписанным; для тестирования sideload его нужно подписать сертификатом с совпадающим Publisher.

## Локально подписанный тестовый пакет

Для локального тестирования создайте сертификат подписи кода, у которого subject и тестовый Publisher полностью совпадают, и поместите сертификат с открытым ключом в:

```text
artifacts/certificates/DiscImageStudio-Test.cer
```

Запустите `Build-MSIX.ps1 -CertificateThumbprint <thumbprint>` с отпечатком сертификата (одновременно заполнив параметры идентичности выше), чтобы создать подписанный пакет. Затем дважды щёлкните `packaging/Install-TestPackage.cmd` или выполните:

```powershell
powershell -ExecutionPolicy Bypass -File packaging/Install-TestPackage.ps1
```

Скрипт установки запросит права администратора один раз, импортирует открытый ключ тестового сертификата в «Локальный компьютер/Доверенные лица» и установит подписанный MSIX. Не отправляйте закрытый ключ или PFX-файл в GitHub и не прикрепляйте локальный самоподписанный тестовый сертификат к официальному Release.

## Быстрое тестирование неподписанного пакета в Windows 11 (необязательно)

Неподписанный тестовый пакет должен использовать отдельное пространство имён издателя OID и не может смешиваться с официальной идентичностью магазина. Создайте локальный тестовый пакет:

```powershell
powershell -ExecutionPolicy Bypass -File packaging/Build-MSIX.ps1 `
  -IdentityName "12345.DiscImageStudioArchitectureTest" `
  -Publisher "CN=Disc Image Studio Test" `
  -PublisherDisplayName "Disc Image Studio Test" `
  -DisplayName "Disc Image Studio Test" `
  -Version "1.0.26.0" `
  -UnsignedDevelopmentPackage
```

Затем установите его из PowerShell с правами администратора:

```powershell
Add-AppxPackage -Path ".\artifacts\msix\DiscImageStudio_1.0.26.0_x64_unsigned-dev.msix" -AllowUnsigned
```

`-UnsignedDevelopmentPackage` используется только для быстрого тестирования в системах Windows 11, поддерживающих эту функцию; некоторые версии Windows могут отклонить исполняемый пакет даже при наличии `-AllowUnsigned`; в этом случае используйте схему с подписанным тестовым пакетом выше. Не используйте этот параметр при подготовке к распространению или отправке в Microsoft Store; официальный пакет всё равно должен использовать реальную идентичность из Partner Center.

Перед официальной отправкой:

- Пересоберите пакет с реальной идентичностью; нельзя отправлять пакет с тестовой Identity.
- Проверьте установку, удаление и работу офлайн на чистом устройстве Windows.
- Запустите Windows App Certification Kit для итогового пакета.
- Предоставьте как минимум один реальный снимок экрана рабочего стола размером 1366×768 или больше.
- Опубликуйте `PRIVACY.md` на общедоступной странице HTTPS и укажите реальные контактные данные поддержки.
- В примечаниях для сертификации укажите, что приложение создаёт большие файлы, не требует входа и не использует сеть, а также содержит экспериментальную функцию прямой записи CD/DVD через Windows IMAPI2; достоверно перечислите поддерживаемые устройства, требования к пустым дискам и текущую область проверки.
